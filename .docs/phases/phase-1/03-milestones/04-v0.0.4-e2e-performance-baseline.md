## Performance

### 계측 도입

- `RequestTrace` / `StartupTrace` → [PRD §72](../../../prd/03-delivery/05-instrumentation.md)
- 파생 지표: `actor_queue_latency`, `spawn_latency`, `readiness_latency`, `proxy_connect_latency`, `time_to_first_byte`
- 게이지: `active_requests`, `pending_requests`, `daemon_cpu`, `daemon_rss`, `open_fds`, `running_apps`
- 구현 수준은 `tracing` + benchmark mode. 상시 metrics framework는 도입하지 않는다.

### 측정 항목

| 측정                   | 내용                                                        | 근거                                                    |
| ---------------------- | ----------------------------------------------------------- | ------------------------------------------------------- |
| direct-backend baseline | Nimwake를 거치지 않은 latency                               | [§42](../../../prd/03-delivery/03-load-tests.md)         |
| warm proxy benchmark    | `proxy_overhead = nimwake - direct`                          | [§42](../../../prd/03-delivery/03-load-tests.md)         |
| cold-start breakdown    | actor queue / spawn / readiness / proxy connect 구간별 분해 | [§42](../../../prd/03-delivery/03-load-tests.md)         |
| concurrency sweep       | 1 → 10 → 50 → 100 → 250 → 500 → 1000, knee point 탐색       | [§42](../../../prd/03-delivery/03-load-tests.md)         |
| CPU / RSS / FD          | daemon 자원 사용량                                           | [§45](../../../prd/03-delivery/07-performance-baseline.md) |
| benchmark report        | release artifact 형식의 리포트 생성                          | [§73](../../../prd/03-delivery/07-performance-baseline.md) |

## 구현 결과

```text
crates/nimwake-core/src/trace.rs   RequestTrace / StartupTrace, 파생 지표
crates/nimwaked/src/options.rs     --apps / --port / --trace-json
crates/nimwaked/tests/
├── harness/mod.rs                 실제 nimwaked를 띄우고 다루는 도구
└── e2e.rs                         E2E 시나리오 14개
crates/nimwake-bench/              warm path / cold-start storm / concurrency sweep + 리포트
.github/workflows/integration.yml  release 바이너리 E2E + 성능 baseline
```

E2E는 in-process 조립이 아니라 **배포되는 바이너리**를 검증한다.
CLI 파싱, tracing 초기화, signal 처리, 종료 순서가 모두 포함된다.

E2E는 `cargo test --workspace`에 포함되므로 **PR CI에서도 돈다.**
따라서 "E2E 실패 시 merge 차단"은 `ci.yml`이 이미 만족시킨다. `integration.yml`은
debug 빌드에서 보이지 않는 것(최적화 빌드의 타이밍, 성능 추세)을 본다.

측정 예 (WSL2, debug 빌드):

```text
warm path       p50 +0.81ms  p95 +1.59ms   (direct 대비 proxy overhead)
cold storm      1000 requests → spawn count 1, unique pid 1, 실패 0
breakdown       actor queue 0.10ms / spawn 0.28ms / readiness 65.05ms
                → 지배적인 구간은 app readiness
sweep           1 / 10 / 50 / 100 … knee point 식별
```

cold start가 단일 숫자가 아니라 구간으로 나온다는 것이 이 마일스톤의 핵심이다.
`65ms` 중 `65.05ms`가 readiness라면 고쳐야 할 것은 Nimwake가 아니라 application이다.

테스트 104개 통과 (unit 39 / daemon options 8 / bench 8 / concurrency 3 / lifecycle 6 /
process runtime 10 / process lifecycle 5 / gateway 11 / **E2E 14**).
