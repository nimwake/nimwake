## 목표

Gateway를 붙여 **request → wake → serve → idle → sleep** 전체 사이클을 실제 HTTP로 성립시킨다.

이 마일스톤을 통과하면 Nimwake의 핵심 가설이 증명된다.

---

## 구현 항목

### Gateway

- HTTP listener (`127.0.0.1:8080`) → [PRD §23](../../../prd/02-architecture/06-gateway-and-requests.md)
- `Host` 기반 routing → [PRD §23](../../../prd/02-architecture/06-gateway-and-requests.md)
- `AppRegistry`
- reverse proxy
- `acquire()` → `RequestLease` → proxy 경로 배선 → [PRD §26](../../../prd/02-architecture/06-gateway-and-requests.md)
- HTTP contract 적용 (GET/HEAD/POST/PUT/DELETE/PATCH 지원, WebSocket·SSE는 미보장) → [PRD §24](../../../prd/02-architecture/06-gateway-and-requests.md)
- `nimwaked` 바이너리 구성 → [PRD §36](../../../prd/02-architecture/09-repository-and-stack.md)

### Scale-to-Zero

- idle timer → [PRD §28](../../../prd/02-architecture/07-scale-to-zero.md)
- `IdleGeneration` 기반 stale timer 보호 → [PRD §29](../../../prd/02-architecture/07-scale-to-zero.md)
- STOPPING 중 도착한 `acquire`를 waiter로 처리 → [PRD §31](../../../prd/02-architecture/08-failure-handling.md)

### Backpressure

- mailbox full → `503` → [PRD §69](../../../prd/02-architecture/06-gateway-and-requests.md)
- `pending >= max_pending_requests` → `503`
- `max_pending_requests`를 manifest에서 재정의 가능

Gateway는 `ProcessRuntime`에 직접 접근하지 않으며, 상태 검사 없이 `acquire()`만 호출한다.
→ [Invariant 3](../../../prd/02-architecture/02-lifecycle-invariants.md)

## Acceptance

```text
curl hello.localhost

→ process starts
→ HTTP 200

curl again

→ same PID

wait idle timeout

→ process disappears

curl again

→ new PID
```

overload:

```text
max_pending_requests 초과 요청

→ 503 Service Unavailable
→ 이미 대기 중인 waiter는 정상 응답
```

---

## 완료 조건

- [ ] cold start 후 HTTP 200 응답
- [ ] warm 상태에서 동일 PID로 재사용
- [ ] idle timeout 후 process 종료
- [ ] 재요청 시 새 PID로 기동
- [ ] active lease가 있는 동안 idle shutdown 발생하지 않음
- [ ] 새 `acquire` 직후 stale timer가 발화해도 종료되지 않음
- [ ] STOPPING 중 도착한 요청이 stop 완료 후 재기동으로 처리됨
- [ ] POST body가 cold start를 거쳐 정상 전달됨
- [ ] pending 상한 초과 시 `503`, 프로세스 추가 생성 없음
- [ ] proxy error / 클라이언트 취소 시에도 `active_requests`가 0으로 회수됨
